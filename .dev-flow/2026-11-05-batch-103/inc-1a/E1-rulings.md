## 1. Scope

**In (PLAN row 1a, US-103-01):**
- **C-D1** — the 3.4 s Ctrl+V. Reproduced on Linux by mechanism (B, pilot P3/P4b): with a threaded Tcl interpreter standing in for the shared Tk root (`tkinter.Tcl()`, created on the main thread like the product's root, no Tk and no `clipboard` command, so no clipboard), the product's own `_read_via_tk` costs 152 ms on the main thread and 3,155 ms in the executor (3 attempts × the 1 s that CPython's `_tkinter` waits for a Tcl main loop before `RuntimeError`); a real Ctrl+V lands after 3,160 ms (one-box app) and 3,252 ms (the real app), against 62 ms and 358 ms with no root. Windows numbers: F §1.4 D1 (3,401–3,483 ms). Pilot P2 shows the other face of the same rule: `eval` from a foreign thread fails at once ("Calling Tcl from different apartment"), while `call`, the path `clipboard_get` takes, waits the 1 s.
- **C-D2** — the Tk write: from the executor it fails after 1,001 ms (B, pilot P3; F §1.4 D2 1,093 ms on Windows), and on the main thread it is a false success that leaves the clipboard owned by an unpumped Tk window (F §1.4 D2).
- **PowerShell by its system path** (batch-102 E5 minor, F §1.5 H6): today `"powershell"` by name (R, `os_clipboard_input.py:131`, `:361`; B pilot P3 prints both). For a bare name Windows searches the folder of the running program and the current folder before the system folder (R, Microsoft's CreateProcess documentation, the search order of `lpCommandLine`), so a `powershell.exe` dropped where the operator starts `s19tui` runs instead.
- **The Linux read path** (D-2): today none that works — with a Tk root every Ctrl+V fails after 3.16 s and pastes the app clipboard, every copy fails after 1.0 s and warns; without a root (no display, hosted CI) the same outcome at once (B, P3, P4, P5).
- **The copy→paste matrix whose source is a text box** (AT-I1a-1 … 8) and **every window and dialog that holds a text box, once** (the 24 walk cases of R-TUI-044.1 and R-PASTE.18). The census (C) sizes it: 48 text-box constructions in `s19_app/`, 40 `OsClipboardInput`, 7 `CappedTextArea` (one of them `JsonHighlightTextArea`), 1 stock `TextArea` (`#patch_json_view`, read-only, Inc 1b), 0 stock `Input`; places: 9 of the 12 rail windows, the command palette, Split / Join / Export, 10 of the 22 dialogs.
- **The paste limit on two paths** (S7 D7-25; D-5 A): a terminal paste into a single-line box and the app-clipboard fallback into a single-line box insert 70,000 characters today (B, pilot3 and P7).
- **The batch-102 copy rows**, which never reached the canon (§4).
- **The Windows CI job** and the test-arrangement rows (R-PASTE.20 … 22).

**Out:**
- Copy from views that are not text boxes (Inc 1b, R-COPY), and the remaining matrix rows.
- Any change of a notice's words (the paste failure warning names "the path" in every box; the write failure warning says "inside the app only" although an OSC 52 request went to the terminal): visible text, BL-I1a-1 and BL-I1a-2.
- `s19_app/tui/screens.py` `LoadFlowScreen._import_external`, which creates and destroys a `tk.Tk()` for each Import (`:1630-1642`): the create/destroy pattern of BUG B7, not a clipboard path; after D-1 A it is the only Tk root in the process (BL-I1a-3).
- A Linux or macOS OS clipboard (D-2 D; BL-I1a-4).

## 8. Risks

- **Hosted Windows clipboard** (open risk of the PLAN): the runner may run without a usable window station clipboard; the probe decides on the first run (R-PASTE.22, D-7).
- **Win32 write with no owner window**: `OpenClipboard(NULL)` followed by `EmptyClipboard` leaves no owner, and Microsoft documents that `SetClipboardData` can then fail. It did not fail on the operator PC (F §1.4 F1). On a PC where it does, every copy falls to PowerShell (≈ 0.2–2.0 s), and R-PASTE.11 fails there. The probe and R-PASTE.2's case record which layer wrote; a hidden message-only window is the design answer if it ever fails (E2 / E3 to weigh, not taken now).
- **Keys queue while a paste is pending**: Textual runs the paste action inside the app's key dispatch (R, textual `app.py:3966-3988`, `:4341-4343`), so a key pressed during a held-clipboard read waits for the read to end (≤ 2.5 s). The screen keeps painting (R-TUI-043.9); a second Ctrl+V pressed meanwhile pastes twice. Normal path: no wait to speak of after D-1.
- **The work PC is a hypothesis**: whether Ctrl+V reaches the app there (F §1.5 H1) is unverified; AT-I1a-10 is the check, and the fix also helps if it is conhost (H2) or a contended clipboard (H3).
- **Timing on hosted runners**: medians of 10 and `timing_bound` (×2 on CI) keep the arms stable; the Tk mutant moves the median by 3 s, far beyond the bound.
- **Lock-in / cost**: none new (stdlib `ctypes`, the system PowerShell, GitHub-hosted runners on a public repository).
