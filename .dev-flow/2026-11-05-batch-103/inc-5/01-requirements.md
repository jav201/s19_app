## User story

**US-103-02 — “After any A2L load or reload, every view that shows A2L labels shows them, with no manual refresh.”** The increment also covers the unload/clear half of the same session contract, the project-A2L replacement question and the visible busy refusal named by PLAN Inc 5.

## Scope and definitions

- **A2L transition:** a completed direct A2L attach; a primary-image load/reload with an A2L attached; a project install; or an unload of `primary`, `mac`, `a2l` or `all`. A project reset is not published as a separate transition: its final project install publishes one coherent state.
- **Common refresh:** the one UI-thread fan-out that refreshes the A2L summary/table, MAC and Issues, the visible Check/Patch parameter prefills, Memory Map, Split / Join / Export and Loaded; invalidates the A2L Detail Card and A2L hex highlight; and leaves unrelated session/work state intact. Function names and ordering are pinned in `E1-rulings.md` and `E1-slice.md`, not in the observable rows.
- **Live view:** a mounted view backed by current session state. Read-back is performed with that view visible; activation alone is not accepted as the refresh trigger for Check or Patch.
- **Same-path reload without clear:** two successful loads of one source path, the second with changed content, with no intervening unload. It is distinct from batch-102's “clear, then re-attach” case.
- **Preserved Loaded/MAC/Issues:** the current primary image and MAC records remain installed when the transition does not itself replace/unload them; their views recompute A2L-dependent values. The active Issues severity filter remains selected.
- **Historical results:** completed check verdicts, before/after reports, flow results and other historical outputs. They are outside this increment; existing generation invalidation is not weakened.
