## 4. The specific findings requested

### 4.1 Stale E4 reconciliation note (documentation defect)
`02-test-cases.md` "E4 reconciliation" (added in the working-tree diff, lines ~5–32) claims: *"The `.148` full measure … is reduced to a **least-of-3 proxy**"* and lists `.148/2–.148/5`, `.148/7–.148/19`, `.150/arr-1–.150/arr-7`, `.150/arr-9–.150/arr-11`, `.151/arr-3–.151/arr-5`, `.136/arr-2`, `.136/arr-3`, `.59/arr-1`, `.63/arr-1` as *"not run as written."* This is **false against the current tree**: `tests/test_b103_a2l_definition_arrays_scale.py:44` sets `LEAST_OF = 15` and `_measure` (`scale.py:135-171`) runs the full least-of-15 interleaved measure for every `.148` case and `.150/arr-1..8,arr-10`; the coverage file provides functional arms for `.148/2..19`, `.150/arr-1..11`, `.151/arr-3..5`, `.136/arr-2..4`. The note predates the supplemental coverage/fix_cap files (note mtime 11:17 vs coverage 11:53, scale 12:06, fix_cap 12:08) and was never re-reconciled.

### 4.2 Missing `.142/5–6` → present but not run
`.142/5` and `.142/6` are **not missing**; they live in `tests/test_b103_a2l_definition_arrays_fix_cap.py:106` and `:159` (the fix-cap file). The original `test_b103_a2l_definition_arrays.py` stops at `.142/4` (`arrays.py:1077`), which is what the "missing" concern points at. However:
- They are marked `serial_timing` but are **not in `scale.py`**; they are a separate untracked file.
- **No execution evidence exists**: neither `zq_iso_user/pytest-serial` nor `pytest-serial-fixed` contains a `test_r_a2l_def_142_*` tmpdir, and `pytest-green-all-functional` only shows `.142/1..4`. So `.142/5–6` are **covered, not_run** — the "pending timing/fix-cap status."

### 4.3 Vacuous / weak assertions
- **`.147/3/6/11` "ok" branch** (`arrays.py:1180-1182`): the only positive assertion is `rule[0] == <keyword>` — a keyword the test itself wrote into the fixture line. This verifies almost nothing about the fixed-point computation.
- **`_messages_bounded`** (`scale.py:177-186`) is defined but never called — dead code; the 1,024-char bound is instead checked inline per case (e.g. `scale.py:451, 465`), so the bound is still enforced, but the helper is misleading.
- `.150/arr-9` corpus half is conditional: `coverage.py:927-935` skips the 168-file corpus when `A2L_CORPUS_FILES`/`~/a2l-corpus/files` is absent; only the inline tables are always verified (`assert checked > 0`). On a runner without the corpus the "119,684 pairs" verification degenerates to a handful of inline pairs.

### 4.4 Fixture-derived expectations
Most expected values are genuinely independent (file bytes via `struct`, the generator's `build_objects` plan, hard-coded pins). Two soft spots:
- The **DEFC tests** `.133/1/.134/1/.135/1` (`decode.py:672-703`) hard-code the plan (`[485,635,696,828,901]`, `[37818,…]`, `[472,132,…]`, `[737,219,…]`) instead of reading `build_definition_objects(rng)`'s `planned_stored`/`planned_text` the way the C08 acceptance test does. They are valid pins (they match the generator's deterministic draws), but they do not cross-check the generator's plan against its own output, and they'd silently pass a model/generator pair that both regressed.
- `test_r_a2l_def_94_3_a2ltool_com_axis` (`arrays.py:791`) and `AT-B103-I3-4` (`decode.py:904`) derive the COM_AXIS expected count from the file's section text (`_axis_pts_max`), which is independent of the model — acceptable.

### 4.5 Timing-harness defects
- **`_measure` absolute bound uses wall clock** (`_timed` default `time.perf_counter`, `scale.py:150`) while E3S3-24 specifies `time.process_time()` for the measure; only the ratio uses `process_time` (`_steady_describe`, `scale.py:98-110`). On a shared host this can false-RED the 0.5 s absolute bound (the exact failure mode E3S3-24 was written to avoid). The ratio part is correct: it times `names[1:]` inside one fresh walk via a lazy generator, and `describe_definitions` does consume `names` lazily (`a2l_definition.py:616-643`), so `_steady_describe` is **not** vacuous.
- **`.142/5` `tracemalloc` peak** (`fix_cap.py:118-127`) takes `max(run_peak)` across three back-to-back `describe_definitions` calls with the same `tracemalloc.start()` — the peak is cumulative, not per-call, which over-estimates (stricter, so not a false-GREEN) but diverges from "peak < 50 MiB" as written.
- **`.142/5`/`6` install no 60 s cap** (acknowledged in `fix_cap.py:24-26`): a regression that re-materializes points would hang rather than time out, leaving "0 timeouts" unenforced by the harness.
- The `.148/1` check never bounds messages, but `.148/1` has no refusal/axes to bound — not a defect.
