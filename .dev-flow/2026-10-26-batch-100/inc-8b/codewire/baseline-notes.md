## Candidates seen while reading (not findings: no run shows them yet)

- **C1 — writers that do not place through `place_into_workarea`.** HLR-171 says the containment check "lives in the one placement function, so no writer is left off a list". The flow save, the chain-set save and the report writers write directly into `<open project>/flows/`, `/flowsets/` and `/reports/` (`save_flow_json`: `flows_dir.mkdir` then `target.write_text`, no containment). At `ebe6d0c` a junction project can be loaded, so these write through it. After 8b the listing and load refusals block a junction project at open time, so these writers are covered only indirectly, and not if the folder is swapped for a junction after the load. Proof owed: an app-level arm (flow save into a junction project opened before the swap) — or the requirement narrows its claim to "every placing writer".
- **C2 — LLR-171.3's negative control is stale at `ebe6d0c`.** P-11 ("a save under another installation's work area is accepted and never listed") was executed at `1d677ba`. At `ebe6d0c` every Save project placement passes `workarea_root=self.workarea`, so a foreign parent is refused by the explicit-root guard (`WorkareaContainmentError` → "Cannot save project: …") — but only after `project_dir.mkdir`, with `_abort_save` removing the folder. The threshold "refused, 0 folders" measured after the call may already hold on base, so TC-B100-33 is not RED on base for a behavioural reason unless it observes the transient folder (a `mkdir` spy) or the refusal token. Same shape as SEC-8 (LED .65, routed to Inc 11). The name-clash scan also reads `self.workarea` while the target is `parent_resolved / cleaned`, so with a foreign parent the clash scan checks the wrong folder.
- **C3 — the single-A2L refusal also refuses the open project's own A2L.** `_handle_save_dialog` (`app.py:9773`) refuses whenever the target holds an A2L and an A2L is loaded. The MAC refusal exempts a file of the same name; the A2L refusal does not. After a project load, `current_a2l_path` is the project's own A2L (`app.py:14439`), so saving the open project again is refused with "Project already has an A2L file." The test helper `_open_project_session` (`test_b100_save_image.py:1308`) records this ("recorded in the increment packet §6"). When 8b moves the refusal to plan time (LED .66), the A2L-only project of AT-B100-10 hits it on any second save into itself. The requirement does not say whether the plan-time refusal keeps this.
- **C4 — "attach the A2L through the A2L load path" has two candidate paths with different outcomes.** `load_a2l_from_path` refuses with "Project already has an A2L file." when `current_project` is set and the project holds an A2L — LLR-171.2's order ("set the project … attach the A2L") makes it refuse its own project; it also copies into `workarea/temp`, so `current_a2l_path` becomes the temp copy, not the project's file, and it calls `_sync_loaded_a2l_to_project`. The image-install path attaches `a2l_files[0]` in place (`_parse_loaded_file`). LLR-171.2 should name which path and the expected `current_a2l_path`.
- **C5 — the save-as sub-folder copy overlaps the document row and the gather.** When the Patch Editor document is `P/patches/boost.json`, `_plan_project_save` plans a document row for Q (`classify_active_document` → `outside`, landing `Q/patches/boost.json`, copied by the gather), and the LLR-171.1 walk also copies `P/patches/boost.json` to the same landing. Whichever runs second reuses the byte-identical file, so its row's action (`new`) disagrees with what happens (`keep`), and TC-B100-59's "rows equal the written tree by full path and action" has two rows for one path. A composition document gathered from the common library under the same name with other bytes lands as `_1`. The plan needs one owner per landing (seam for E2).
- **C6 — the per-file cap on sub-folder copies.** `place_into_workarea` refuses files over `DEFAULT_COPY_SIZE_CAP_BYTES` (256 MiB, `workspace.py:70`) with `WorkareaPlacementError`, which aborts the whole save. LLR-171.1 checks only the total against free space. A large file under `splits/` would abort a save-as that the plan accepted. Low likelihood; the plan should refuse it up front or the requirement should state it.
