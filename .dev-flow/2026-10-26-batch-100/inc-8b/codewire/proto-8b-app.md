## Findings

finding F-1 _manifest_carry needs no change for the save-as carry
anchor: S19TuiApp._manifest_carry
seen: read at ebe6d0c (:11570–11630): every record is made relative to the folder it was read from; the save-as copy keeps each file at the same relative path.
cause: relative text does not depend on the project root.
effect: calling it on P gives text that is valid in Q; the change is the caller (the handler's step 4 and 13), not the function.
decision: node kept as unchanged with a new caller; E1 §3 row 3 ("used for a save as too") is met by the call.

finding F-2 the fixed interface gives G1 no list of files to copy
anchor: S19TuiApp._copy_project_subfolders
seen: interfaces-8b: `ProjectInventory` holds folders (name, count, links) and one byte total; `SavePlan` gains folders, skipped links and total_bytes. Neither names the files.
cause: the interface describes what the plan paints, not what the handler executes.
effect: without a file list G1 must walk P a second time at execution, which can disagree with the plan's counts (R-PC) and cannot honour "the document row owns its landing" (the exclusion is decided in the planner).
decision: Proposed change P-1. E3 r1: decided by pre-ruling 1 (`InventoryFile(relative, size)`, `SavePlan.copies`); the node `_copy_project_subfolders` executes it.

finding F-3 ProjectInventory.total_bytes counts the wrong bytes for the save-as total
anchor: S19TuiApp._plan_project_save
seen: interfaces-8b: `ProjectInventory.total_bytes` = regular files at all depths "incl. top level". LLR-171.1i: the total is the top-level files the save writes, the EMITTED image and the sub-folder files.
cause: P's top level holds files the save does not write (other variants, project.json, kept manifest copies) and the source image, not the emitted bytes.
effect: a total taken from the inventory fails LLR-171.1i's negative control ("source image instead of emitted") and over-counts other variants.
decision: Proposed change P-4: `SavePlan.total_bytes` = Σ PlannedFile.size of the top-level rows + Σ PlannedCopy.size; the inventory total counts sub-folder files only (or goes). E3 r1: decided by pre-ruling 2 (`ProjectInventory.total_bytes` dropped), with G2's rule "the planned rows whose action is new + the copies" (A3-14) and each file rounded up to 4 KiB plus 64 KiB (R7).

finding F-4 the per-file cap raises WorkareaContainmentError, not WorkareaPlacementError
anchor: place_into_workarea
seen: `workspace.py:1116-1118` (`size > max_size_bytes` → WorkareaContainmentError "Refusing to copy …"); baseline-notes C6 says WorkareaPlacementError.
cause: wording in C6.
effect: none for the design (the plan refuses first; the handler's excepts catch both); the cap boundary is `>` in the placement, matching LLR-167.6g.
decision: recorded; no change.

finding F-5 Save project never republishes the flow panels' session folder
anchor: S19TuiApp._handle_save_dialog
seen: `_publish_flow_session_dir` has one caller, the load (:11427). After a save as, `current_project_dir` is Q but the Flow panels' session strip still shows P. The flow lists themselves read `active_project_dir()` when opened (:3398), so they read Q.
cause: older than 8b.
effect: AT-B100-09's "Q's flow list shows f1" passes even if the list were read from P unless the AT tells them apart (P's "flows/f1.json" also exists).
decision: AT-B100-09 should assert the list's folder is Q (or remove "P/flows/f1.json" after the save and still see "f1"); the stale strip goes to the backlog (not 8b scope). E3 r1: superseded — AT-B100-09 removes "P/flows/f1.json" after the save (A3-10), and a completed save as republishes the session folder in 8b (R9, LLR-171.1l).

finding F-6 derived_from is not carried by a save as
anchor: S19TuiApp._handle_save_dialog
seen: ruling Q7 lists 5 records; `derived_from` (LLR-168.4) is not among them. An unchanged image copied from P to Q loses P's record of its base.
cause: scope of Q7.
effect: Q's `derived_from` holds only this save's emit record.
decision: follow Q7; E3 confirms or adds the key. E3 r1: added by pre-ruling 9 with A3-8's two lines (the flag from the source carry; only records whose key names a top-level data file Q holds), the scope widened by R3 because P's other variants are now copied.

finding F-7 the R3 top-level copy needs an exclusion rule for the companion files and keeps P's manifest copies
anchor: plan_project_save
seen: R3 copies every top-level regular file of P that the save does not write itself (not the image / MAC / A2L rows, not `project.json`, not a link). P can hold a MAC or A2L with another name than the session's (a session MAC loaded from elsewhere); copying it beside the MAC row would give Q two MAC files, which the variant rebuild's `validate_project_files` then rejects after `mkdir` (the A3-17 shape: "Saved" over no manifest).
cause: R3 names the rows, not the file kinds; LED .63 (b) / .66 hold Q to one MAC and one A2L.
effect: this pass reads "the image / MAC / A2L rows" as: a top-level file whose name equals a top-level row's landing name is left out, and when the plan holds a MAC row (A2L row) every top-level MAC (A2L) file of P is left out; without a session MAC (A2L) P's file is copied. `project.json.previous-<UTC>` copies are regular files the save does not write, so they are copied (R3 read literally).
decision: applied as stated in G2 `plan_project_save` step (4a); E3 round 2 confirms both readings. E3 r2: the companion rule is confirmed (R10); backups are not copied (R10, A3R2-2, S3R2-2): `inventory_project_tree` leaves `project.json` and every `project.json.previous-*` name (`normcase`) out of `top_level` and out of the stop count.

finding F-8 a copied top-level variant can be reused by the image row and abort the save
anchor: S19TuiApp._handle_save_dialog
seen: with R2 + R3 the top-level copies land before the rows loop. The image row of a save as is predicted against the empty Q, but `find_identical` lists `<stem>_<digits><suffix>` candidates: if P holds "firmware_1.s19" byte-identical to the image this save writes (an earlier emit of the same patch), the placement reuses "Q/firmware_1.s19" while the plan named "Q/firmware.s19".
cause: the copy fills Q's top level before the top-level rows are placed; the prediction does not see it (A3-9 rejects a second name-list predictor).
effect: `_plan_row_mismatch` aborts the save and rolls back: loud, never silent; saving again fails the same way until the identical variant is removed.
decision: recorded for E3 round 2 (options: predict the top-level rows of a save as against the copy list's top-level names, or place the top-level rows before the top-level copies while the sub-folder copy stays first). E3 r2: R11: the top-level copy runs after the rows loop (handler step 12b), and each top-level landing is checked with `_plan_row_mismatch` (A3R2-1, A3R2-5).

finding F-9 the R1 ceiling bounds the count, not the time
anchor: S19TuiApp._copy_project_subfolders
seen: P1 of E3-security measured 6.0–8.8 ms per copied file on the main thread; 2 000 files in one folder take an estimated 12–18 s (extrapolated, not run).
cause: Save project runs on the main thread with no progress; a background copy with progress and cancel is Inc 12a (R1).
effect: a save as at the ceiling freezes the app for seconds; no requirement bounds it in 8b.
decision: E4 measures the 2 000-file save on the shipped code and reports the time (not gated); the worker stays with Inc 12a.

R-2 (seam G1↔G2, one owner per landing, C5, LLR-167.6e). Under the fixed rule the document row owns its landing and the copy leaves that path out. When P holds a DIFFERENT file at the document's landing (P's older "patches/changes.json" while the session holds a new pasted document; or P's "patches/boost.json" differing from the common-folder "boost.json" the session opened), Q gets the session document and lacks P's file: LLR-171.1's "100 % of the expected set" fails for that one path, silently. Recommendation (no digests needed): G2 lists the left-out path in the plan and G1 paints one status line ("patches/changes.json of P was not copied — the Patch Editor document is saved at that path"); or E3 rules that the pasted document's landing is predicted against the copy list (lands `changes_1.json`), which needs one digest of the colliding P file to tell reuse from `_1`.
R-3 (seam G1↔G2, P-4 / F-3). `total_bytes` must be the bytes this save writes, not the inventory total; otherwise LLR-171.1i's negative control is not RED for a behavioural reason.
R-4 (cap value in two places). The plan's cap (G2) and the placement's default cap (`place_into_workarea`'s default argument, bound at import) must be the same number. The test lowers the cap; if it patches `workspace.DEFAULT_COPY_SIZE_CAP_BYTES`, only a reader that looks the constant up at call time sees it. G2 should read `workspace.DEFAULT_COPY_SIZE_CAP_BYTES` at call time; the placement keeps its default (it never sees an over-cap file once the plan refused).
R-5 (Inc 8a rule, E3 R12 spelling). Rebinding the parent to `self.workarea` changes `project_dir`'s spelling when the operator typed another spelling of W. The 8a bind (`project_dir / home / name`, unresolved) then uses W's own spelling, which is the load's spelling: the in-home test of the next save sees one spelling in more cases than at ebe6d0c, not fewer. TC-B100-29's E3 R12 arm (junction above the anchor) is unchanged because it saves under W's own spelling.
R-6 (listing containment arm). `list_projects` calls the full shared check; for a direct child that is not a link the `outside` arm cannot fire, so a mutant removing it from the listing survives. Kept on purpose: one check with one meaning (HLR-171b), and the load (LLR-171.4f) covers the arm. E3 may rule the listing to the link arm only.
R-7 (A2L-only with an unreadable A2L). The parse (:11316) runs after the reset (as for every project load at ebe6d0c). An A2L-only folder whose A2L does not parse ends at the "nothing installable" line with the session already reset and no project opened. No requirement covers it; options: (a) keep (consistent with today's second "No supported files" return after a reset), (b) parse the A2L before the reset for the A2L-only branch so the refusal resets nothing. Recommendation: (a) for 8b, backlog (b).
R-8 (LLR-171.2d condition). LLR-171.2d says "whose project.json records no missing file"; the design paints `no data or A2L file` whenever project.json exists and the folder holds neither file, also when the manifest records a file that is now missing. No requirement states the other arm; E3 confirms one line for both, or adds the `missing` names.
R-9 (Inc 7 rule, the plan executed exactly). The MAC / A2L checks leave the save body. A MAC or A2L that appears in a merge target between the plan and the placement is no longer refused (the plan said no). Race only; same TOCTOU class as 8a R-15. The placement still places it (`_N` if the name clashes), and `validate_project_files`' two-MAC error still fires after `mkdir`.
R-10 (dialog selection vs carried records, LLR-171.1h). The design writes the dialog's batch / assignments when the operator selected something, else P's records. At ebe6d0c the selection lists start unselected (`screens.py:572`), so an open-project save with no selection writes an empty `batch` (candidate C-7 below). For a save as, "carry unless selected" means the operator cannot clear the batch in the same save; E3 confirms.
R-11 (status line length). Row 7 names every skipped link in one line; a project with hundreds of links gives a long line. The status log clips at the terminal width (LED .64); the test reads the whole message. No cap proposed (the requirement names each link).
R-12 (records behind a skipped link). A carried record (`batch`, `gathered`, `active_document`) naming a file under a skipped link is carried, and Q's next Load lists it as `missing`. Honest ("restore the file, or Save project to drop it"), not filtered. LLR-171.1h's fixture has no such record.
R-13 (free-space check scope). The check runs for every `new` target (a save as, and a first save from a fresh session, whose total is the top-level files only). Same rule, one branch; a fresh-session save into a full disk is now refused before `mkdir` instead of failing after it.
C-7 (candidate, not a finding: no run shows it). `_handle_save_dialog` writes `payload.batch` and `payload.assignments` for every target; the dialog's lists start unselected, so a Save project into the open project with no selection may write an empty `batch` over P's. Outside 8b; to probe before E3 if R-10 is ruled on.

### Proposed changes to interfaces-8b.md
P-1 (G2, F-2, R-1). `SavePlan.copies: tuple[PlannedCopy, ...]` with `PlannedCopy(rel: str, size: int)`: the project-relative POSIX path and size of each regular sub-folder file to copy, link-free, after the one-owner rule removed the document row's landing; empty unless the target is new and an inventory was passed. `ProjectInventory` gains `files: tuple[PlannedCopy, ...]` (all regular sub-folder files with sizes), from which the planner builds `copies`, the folder counts and the cap check. `PlannedFolder.file_count` = the number of `copies` under that folder.
P-2 (G1 → G2, LLR-167.6f). `plan_project_save(..., a2l_exempt: bool = False)`: G1 computes the own-A2L fact (same file, or same name and same bytes) because it needs the target A2L's digest; G2 keeps the decision and the tokens (target holds an A2L, the session plans an A2L row, and not `a2l_exempt` → the refusal). The MAC rule needs no extra input (the names are in the target listing and the MAC PlannedFile).
P-3 (G1 → G2). `plan_project_save(..., inventory: Optional[ProjectInventory] = None)`: G1 calls `inventory_project_tree(P)` only for a new target with an open project that passes `_project_folder_refusal`, and passes `None` otherwise (LLR-171.1g: then folders, copies and skipped links are empty).
P-4 (G2, F-3, R-3). `SavePlan.total_bytes` = Σ size of the top-level PlannedFiles the save writes (the emitted image's payload size, the MAC, the A2L, a pasted or copied document) + Σ `PlannedCopy.size`; `ProjectInventory.total_bytes` counts sub-folder files only, or is removed.
P-5 (G2, R-2, optional). `SavePlan.left_out: tuple[str, ...]`: sub-folder paths the one-owner rule removed from `copies` because the document row owns that landing and the source file is not the document itself; G1 paints one line naming them. Only if E3 keeps the document-owns rule for a different file.
