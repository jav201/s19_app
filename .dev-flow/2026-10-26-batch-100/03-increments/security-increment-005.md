## Questions asked of this diff

1. **Can a rollback delete anything it did not create?** It did not in any executed case. One benign exception is noted under E2 below.
   - **D1: reuse, then a forced manifest failure in the open project `M`.** The pre-existing `firmware.s19` was REUSED (plan `keep`), and the rollback left `M` unchanged: diff `{}`, every file byte-identical.
   - **D2: a concurrent writer at the planned landing.** A foreign file was planted at `C\firmware.s19` just before the emit. The emit dedup-landed elsewhere, the plan-row check refused the save (`the plan named …\C\firmware.s19 (new) but the file landed …`), the rollback removed only the save's own file, and the foreign file survived intact.
   - **E2: the folder this save created was swapped for a junction before placement.** The guard refused. The rollback's `rmdir` then removed the **junction itself**, not its target, and the other work area's file is intact. The rollback did remove a link it did not create, but no data was lost. I record this and raise no finding for it.
   - The rollback's limits are the other way round: it can **miss** something it created (SEC-7).
2. **Can a plan row's destination escape the work area?** No.
   - A plan row is never a write target. Copies place `row.source` into `project_dir` through `place_into_workarea(…, workarea_root=self.workarea)`. The emit uses only `row.landing.name`, which `_sanitize_s19_filename` re-sanitises.
   - `row.landing` is only compared with the landed path (`_plan_row_mismatch`, `normcase`).
   - `sanitize_project_name` keeps only `[alnum - _]`, so `..`, separators and absolute names cannot reach `cleaned`.
   - Junction, upper-case and pre-resolved spellings were refused at the emit guard (C2–C4, A3–A4). See SEC-8 for what happens before the guard.
3. **Is any path resolved or followed before the guard runs (plan vs. run)?** Yes, in two places, and both are covered by SEC-8:
   - The **plan** reads the target before any guard. `predict_placement` lists the target and hashes same-size candidates, and `plan_project_save` calls `Path(target).resolve()`. These are reads only.
   - The **`mkdir`** of the project folder runs before any containment guard. That ordering is pre-existing.

   Swapping the target for a junction after the plan was refused, with 0 entries outside (E1: planted before `mkdir`; E2: after `mkdir`). The rollback did not touch the planted junction in E1, because `created_project_dir` was False.
4. **Are secrets or private paths written into the evidence?** No secrets. No operator name. No key material.
   - A grep of `evidence/inc-5/`, the packet and the new test module for names, keys, tokens, passwords, and private-key headers found only `test_tc608_tokenizer…`, a test name.
   - There are no Drive or vault paths.
   - The transcripts do contain absolute local paths with the Windows account folder: 620 occurrences in `evidence/inc-5/`, including this review's copies. That matches every earlier increment's evidence. It is informational for a public repo, not a finding.
