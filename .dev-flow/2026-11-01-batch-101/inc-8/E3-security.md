## Answers to the focus questions

| Question | Answer |
|---|---|
| Copy destination contained in the work area; junctions (the D15-18 class) | **Yes.** The copy goes through `place_into_workarea`, whose `_guarded_destination` runs on the project folder as given and refuses a junction or link on the way; every claim is `lstat`-checked before and after. The D15-18 class (a home folder that resolves outside the work area) does not apply to this writer. |
| Copy source (relative output, D15-17 / D-5) | A source leaf that is a link is refused; a parent junction and `..` are followed. No reach beyond what an absolute output already has. See S-3. |
| A later block reading the copy | The copy is the placement's own result (regular file, inside the guarded destination). The rebind skips the per-read guard of `_resolve_manifest_entry` for that path. See S-4. |
| Names from user-controlled files | The copy name is the output's own name (flow file plus bench file). It reaches summaries, `change_doc_ref` and reports. Every sink read is markup-off or escaped. See S-7. The rebind by name can substitute a bench file for a project input with no record. See S-2. |
| Config/template file reads (size, JSON) | Flow CRC read has no size limit (O-1). This is not new, and the per-block `except` catches the failure. Deep JSON nesting raises `RecursionError` out of `parse_crc_config`, and the Operations Execute handler does not catch it. This is also not new. See S-5, S-6. |
| Error texts echoing file content | **The design removes an existing length bound.** See S-1. |
| Could the CRC change let a wrong image pass a check silently | **No.** There is one computation site (`crc.py:211`, grep), and the change only affects `reverse: true` with an init that is not bit-symmetric. Images written by earlier versions now give MISMATCH, so the failure is visible. The remaining risk is to availability, not integrity. See S-8. |
