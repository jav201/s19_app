## 1. Scope

In scope:
1. **F-23, CRC Designer.** Three causes, each read in the code:
   - **Recomputes per action.** Every `Input.Changed` / `Switch.Changed` / `Select.Changed` in the panel calls `_recompute` at once (`crc_designer_view.py:615`, `:627`, `:560`). A template load sets up to 11 widget values (`_apply_template` → `_apply_algorithm`, `:1312`, `:519`), each posting its own change event, so one load runs about 11 recomputes plus the explicit one; a preset pick about 9. Typing runs one recompute per keystroke.
   - **CRC passes per recompute.** `_coverage_preview_text` (`:951`) runs `evaluate_target` (one window read + CRC) and `compute_target_crc` twice; `_render_coverage_window` (`:1009`) runs `compute_target_crc` twice and `evaluate_target` again: **6 window reads and CRCs per recompute** (the plan's "4×" counted only the explicit calls). In the ch12.4 scene the concat window is 1.2 MiB and the fill window about 4 MiB (the fill pads the 2.8 MiB between `0x00931FBF` and `0x00C00000`), so one recompute digests about 12.8 MB.
   - **The engine's per-byte cost.** `crc_lut` (`operations/crc_kernel.py:187`) calls `reflect(byte, 8)` (a Python function with an 8-step loop) for every input byte when `refin` is true, as for the default CRC-32/ISO-HDLC. Estimate: about 1 µs per byte, so 12.8 MB ≈ 10–13 s, which matches the guide's 10 s.
   Design: (a) operator text edits and image changes recompute once, the quiet time (150 ms) after the last of them; toggles, dropdowns, a preset pick and a template load recompute at once and exactly once (fills run with the widgets' change events suppressed); (b) one coverage computation per recompute, shared by the preview and the window: at most 2 window reads (the evaluation's CRC is the active policy's; only the other policy is computed again; when the abort policy refuses, concat and fill are computed for the window's line 2); (c) the engine reflects all input bytes at once through a 256-byte table. Estimated result for the ch12.4 scene: 5.2 MB digested at about 0.15–0.25 µs per byte plus the 1.2 MiB gather, about 1.0–1.6 s per recompute (bound 3 s).
2. **F-24.** The panel recomputes only on its own events and on mount (with no image, at startup); no hook runs when the image is loaded (triage, confirmed: `CrcDesignerPanel` is referenced only from compose, `app.py:3867`). Design: the panel watches the app's `current_file` reactive (`app.py:2748`) and treats an image change as a pending change (recompute after the quiet time). The app already watches the same reactive for the Split/Join window (`app.py:17851`), so this is the app's own pattern, from the panel's side.
3. **F-23, Split/Join.** In the ch14.6 scene (`range_00` and `range_02` ticked, join fill, pad 0x00), `range_01` (2.79 MiB) lies in the join gap. `_conflict_marks` (`segment_split_view.py:316`) walks it byte by byte in Python, rebuilding a tuple per conflict byte; the app region's bytes break into many conflict runs wherever a byte equals the pad (0x00 runs), and `_sweep` (`:288`) then classifies every elementary interval against every mark: **O(intervals × marks)**, about 2·m² steps for m marks. With some 10⁴ runs that is about 10⁸–10⁹ steps, the dominant share of the guide's 25 s (to be confirmed by M-2). `refresh_window` syncs twice on open (`:1678`), and every key runs one more sync. Design: `_sweep` becomes a sweep over sorted boundaries (O(m log m)); `_conflict_marks` builds each source∩gap window with C-level calls (`bytes(map(mem_map.get, range(lo, hi), repeat(pad)))`; an absent address and a pad-valued byte both read as the pad, exactly the base predicate `addr in mem_map and mem_map[addr] != pad`) and finds the non-pad runs with one compiled regular expression; adjacent runs merge as on base.

Out of scope (with where it goes):
- **A worker for either view.** Ruled out at P0 ("no worker"); the estimates put both scenes well under their bounds without one.
- **The coverage gather's per-byte dict walk** (`crc_designer_model._gather_range`, about 0.1 µs per byte, ≈ 0.15 s per 1.2 MiB read). Not needed for the bound; `crc_designer_model.py` stays untouched.
- **In-place byte changes do not refresh the CRC Designer.** `current_file` is assigned in three places only (`app.py:13434`, `:17189`, `:17954`); an apply of a change document changes `mem_map` in place (`changes/apply.py:341`, `services/change_service.py:1848`, `:2366`) without a new assignment, so after an apply the coverage CRCs stay stale until a field changes. Same class as F-24, not the reported scene; **not verified by a run.** Routed to **Inc 5** with integrity priority (D-4 below, E3 ruling SEC-3).
- **The band draws one cell per run when runs outnumber cells** (`apportion`, `segment_split_view.py:1008`: `width < n → [1] * n`): in the ch14.6 scene the band line is thousands of cells long and the widget crops it. A render question, not a cost the bound needs; **not verified by a run**; noted for the KF review. Test input for that backlog item (E3 ruling SEC-7): an image whose join-gap source alternates pad and non-pad bytes (one conflict mark per 2 bytes, ≈ 1.4 M marks over the demo's 2.79 MiB gap).
- **D17-24** (split-mode band with gaps skip shows fill) stays as on base: this increment changes no render. The invariance oracle therefore compares with the base plan, not only with the canon classifier (E1-D6).
- **D13-31** (`Invalid parameters: <field> is not a number: <text>`) stays open: the shared coverage computation keeps today's `Invalid parameters: <exception text>`.

**What the operator can notice.** (1) While typing in a CRC Designer text field the result surfaces update 150 ms after the last keystroke (today: after each keystroke, which with the demo image freezes the screen). This is the plan's ruled target ("1 per 150 ms burst"); the painted texts do not change. (2) An image loaded while the CRC Designer is not displayed is recomputed when the CRC Designer is next displayed (the quiet time after the display), not at the load, so a load on another view costs nothing here (E3 ruling A-6, R-CRC-PREVIEW-002.5). (3) A coverage whose size exceeds 16777216 bytes (16 MiB) shows `Cannot preview: coverage exceeds 16777216 bytes` in the preview and as line 2 of the window instead of being computed (E3 ruling SEC-2, R-CRC-PREVIEW-001.11; base freezes or crashes). The 67108864-byte / 64 MiB figures in §5 M-0 are the measured window and stay as history (corrected at the E5 re-audit). (4) Ranges not in ascending address order draw line 1 of the window at the scale of their whole span, at most 48 glyphs per run (E3 ruling SEC-1, R-CRC-PREVIEW-001.12; base draws up to one glyph per byte and freezes or crashes; ascending Ranges draw as on base). No other screen changes.

## 3. Decisions taken at E1 (with reasons)

- **E1-D1 — a third source file: `operations/crc_kernel.py`.** The plan row names two files. By the estimate of §1, sharing the computation alone leaves the ch12.4 recompute at about 5–6 s (5.2 MB at ≈ 1.1 µs per byte), and the table alone at about 2–3 s (12.8 MB at ≈ 0.2 µs), under 20 % margin; both together ≈ 1.0–1.6 s. The change is one statement in `crc_lut` plus a module constant, result-identical by construction (the table is `reflect(b, 8)` for each b), and pinned by the existing differential tests (`tests/test_crc_kernel.py:110`, `:122`, `:129`). No open increment owns the file (Inc 8 merged; Inc 4–6, 9–12 own `app.py`, services and screens; Inc 11 and 14 own A2L and help files). 3 files of the cap of 4. **Needs the orchestrator's approval (D-1).**
- **E1-D2 — the quiet time applies to text fields and image changes only.** Alternatives weighed:
  - *Every change after the quiet time* (Save dialog precedent, `screens.py:1156`): one path, but a toggle would wait 150 ms for nothing and every existing test that flips a dropdown and reads at once would need a wait.
  - *Recompute at once while the work is small, after the quiet time while the coverage is large*: fewer test edits, but two behaviours with a size boundary to specify and test, and the rule depends on the image. Rejected (simpler wins).
  - *Only the coverage surfaces after the quiet time*: the screen would show a fresh verdict beside a stale coverage window for 150 ms, and an invalid parameter would paint in two steps. Rejected.
  - **Chosen:** a keystroke-driven field waits for the quiet time (the precedent's case: typing); a discrete choice recomputes at once and supersedes any pending timer (the Save dialog's `_recompute` stops its trailing timer the same way, `screens.py:1329-1334`). The quiet time is a module constant (`CRC_RECOMPUTE_S = 0.150`, mirroring `SAVE_RECOMPUTE_S`) that tests inject, as `tests/test_b100_save_dialog.py:561` does.
- **E1-D3 — fills suppress their own change events.** `_apply_template` and the preset path set the widgets inside Textual's public `MessagePump.prevent(Input.Changed, Switch.Changed)` (Textual 8.2.8, the dev pin: `post_message` returns without posting when `Widget.check_message_enabled` finds the type prevented, `message_pump.py:877`, `widget.py:4663`), then recompute once. Deterministic, no timer. Checked: the app's own `on_input_changed` (`app.py:20486`) acts only on `a2l_tags_filter_input` and `a2l_tag_find_input`, so suppressing the CRC fields' events changes nothing else.
- **E1-D4 — F-24 by watching `current_file` from the panel, not by an `app.py` hook and not by `Show`.** An `app.py` hook would enter the serial `app.py` chain (Inc 4 → 12) for one line. A `Show` handler would recompute on every visit to the screen (about 1.2 s with the ch12.4 coverage) and, after a modal load dialog, `Show` is not re-sent to a screen that stayed visible. `DOMNode.watch(self.app, "current_file", …, init=False)` is public API; the app's own `watch_current_file` (`app.py:17851`) shows the reactive fires on every install and unload. **E3 ruling A-6 / SEC-2:** the watcher schedules a recompute only while the panel is on screen (Textual 8.2.8 `Widget.is_on_screen`, `widget.py:2450`); otherwise it marks the coverage stale, and the panel's `on_show` (`events.Show`, posted by `Screen._refresh_layout` for a widget the reflow shows, `screen.py:1380`) schedules one recompute when the flag is set. This is not the rejected recompute on *every* show: a clean display costs nothing. **Residual** (§1, out of scope): in-place byte changes, routed to Inc 5 (D-4, E3 ruling SEC-3).
- **E1-D5 — no result cache in either view.** `mem_map` is changed in place by the change apply (§1), so a cache keyed on the image object would show stale results. Both views compute every time, fast.
- **E1-D6 — two oracles for the band.** For join fill (where the conflict class lives) the band is compared with a per-address classifier written from CTX-SJE-BAND (independent of the code). For every mode, the plan is compared with the base reference (the base `_sweep` and `_conflict_marks` copied verbatim into `tests/support/`), because the split-mode skip band (D17-24) differs from the canon on purpose until a UI round fixes it; the increment must change no render.
- **E1-D7 — the 10 MB scenes are built from the generator, not parsed.** `compute_region_sizes(10)` + `build_objects(regions, random.Random(20260001))` give the bytes of the shipped demo `firmware.s19` without writing and parsing 10 MB of S19 text (the generator's `generate` runs the same two steps first, `tools/synth/make_release_case.py:1018-1019`). One module-scoped fixture serves all three arms.
- **E1-D8 — existing test bodies that read a surface right after a text edit get a wait; names and assertions stay.** With the quiet time, a node that sets a text field and reads a result surface after one `pilot.pause()` reads the old value. `E1-slice.md` §3 lists the 12 nodes and 3 helpers found by reading `tests/test_crc_designer_view.py`; each gets one snapshot of the recompute count before the text edit and one wait for the recompute after it (the shared helper of `E1-slice.md` §2 T6: `wait_until(…, pause_first=True)` until the recompute count is above the snapshot and no recompute is pending, E3 ruling A-3; never a fixed sleep as `tests/support/b100_save_dialog.py:132` does), no assertion changes. The evidence that nothing else changed is an AST compare against the base (E3 ruling A-1; `E1-slice.md` §3). E4 confirms the list by running the module on the change and edits only the nodes that turn RED for that reason. **Needs the orchestrator's go, because it edits existing node bodies (D-2).**
- **E1-D9 — the timing arms' clock.** Each arm stops at a stamp the product emits (engineering rule 3): the `update` of `#crc_coverage_window` or `#sje_stats` after the trigger, recorded by a wrapper of that widget's `update`; it starts at the trigger statement. Each arm is marked `serial_timing`, uses `timing_bound(...)`, and calls `report_margin` once per bound (QC-TM).
