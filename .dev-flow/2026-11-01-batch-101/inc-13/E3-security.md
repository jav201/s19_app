## Verdict

**PASS-WITH-NOTES.** No HIGH finding. The design does not open a path that writes a wrong CRC: the designer never writes firmware (only Save writes the `*.crc.json`, from the live fields with its own KAT, `crc_designer_view.py:1191-1261`), the shared `_CoverageRun` is computed from the live form and image at fire time with no cache (E1-D5), the Split/Join export keeps an engine-side abort independent of the band (`segment_ops.join_fill` → `gap_conflict` → `GapConflictError`, `segment_ops.py:364-388`), and the kernel's table is pinned over all 256 byte values by the existing differential vectors. The three MEDIUM findings are pre-existing availability/staleness issues that this increment's code touches or makes more reachable; none needs to block E4, but SEC-1 and SEC-2 need an orchestrator ruling (fold or backlog).

## Rows and tests (security lens)

- No row bounds the coverage size or the window glyph count; SEC-1 and SEC-2 are where those rows would go. R-CRC-PREVIEW-001.8 covers only the rules `_build_target` already enforces.
- The timing arms' oracles are independent (`zlib.crc32`, the engine's `gap_conflict` count), so a fast wrong CRC or conflict count fails (R-CRC-PREVIEW-002.2/1, R-SEG-PREV.20/1). Good.
- The matrix (R-CRC-PREVIEW-001.2/2, .3/1) uses two distinct oracles (`0x9C5BCBBD` / `0x2A8A3950`), so a concat/fill label swap or a wrong-policy store word fails (M-9). Good.
