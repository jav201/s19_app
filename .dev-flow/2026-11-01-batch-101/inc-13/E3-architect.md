### Cap value (SEC-2): recommend **4718592 bytes (4.5 MiB, `0x480000`)**

Arithmetic, from M-0's measurement (one fully gathered 64 MiB window read = 6.12 s gather + 10.10 s CRC = 16.22 s):
- Per byte, one read costs 16.22 s / 67108864 B = **0.2417 µs/B**. A recompute does at most 2 reads (R-CRC-PREVIEW-002.2/2), so the worst case is **0.4834 µs per byte of coverage size**. Gap bytes cost less: the pad is built in bulk, the CRC (0.150 µs/B) runs once in the fill read, and the 2 gap walks cost 0.082 µs/B each (0.24 s over the 2940993-byte F-23 gap). That is ≈ 0.31 µs/B, so a coverage of present range bytes only is the worst case.
- Budget: the 3 s bound, less the QC-TM 20 % margin, is 2.4 s; keep ≈ 0.1 s for the widget updates, which leaves ≈ 2.3 s of compute. The cap is then ≤ 2.3 s / 0.4834 µs = 4.76 MB.
- Candidates, worst recompute: 4 MiB → 2.03 s, but it refuses the F-23 scene (its coverage size is 0x400FFF = 4198399 B > 4194304); **4.5 MiB → 2.28 s ✓**, with the F-23 scene under it (520193 B, 11 % headroom); 5 MiB → 2.53 s (margin 16 % < 20 %); 64 MiB → 32.4 s.
- Peak memory at 4.5 MiB is ≈ 14 MiB above the image (M-0 measured +184 MiB at 64 MiB).

Consequence (state it in "What the operator can notice"): a coverage above 4.5 MiB is refused with the text instead of being previewed. That covers a whole-image coverage of the demo with Join gaps fill (≈ 12 MiB) and boot + app + cal (≈ 9.2 MiB). The app region (2.79 MiB), the calibration region and the F-23 scene still preview. If the operator needs whole-image previews, the alternative is a safety-only cap (for example 16 MiB, ≈ 8 s worst case) with the 3 s target stated for coverages ≤ 4.5 MiB. That is an operator decision; the constant is reversible. M-0's sentence "a smaller cap would refuse legitimate coverages above it" is true but does not weigh the target; replace it with this arithmetic.
