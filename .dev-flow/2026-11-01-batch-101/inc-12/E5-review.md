### R-7 — a pre-existing double-dismiss race now has one more trigger on Reports  [LOW · security / robustness · outside the slice, backlog]
- **What:** Escape cannot land between Generate's post and its dismiss (check 10). It can, though, reach the app's binding check **before** a Generate `Pressed` already in flight reaches the dialog. The dialog then pops, and Generate's handler later runs on the popped dialog. It posts `GenerateRequested`, so a report is written; the operator did press Generate. Its own `dismiss` then raises `ScreenStackError` ("Can't pop screen; there must be at least one screen on the stack"). Textual's `Screen.dismiss` does not check `is_active` (`screen.py:2048-2081`), and `pop_screen` raises at stack depth 1 (`app.py:3103-3107`).
- **Where:** `s19_app/tui/screens.py:3093-3095` (the new trigger) and `:3404-3427` (the handler that raises).
- **Scenario and evidence:** the race probe. (B) `press()`, then the Escape action in the same tick: the handler ran with `active=False stack=1`, and its `dismiss` raised `ScreenStackError`. (A) `pilot.press("enter", "escape")`: benign, because the pilot idles between keys, so this needs both keys delivered while the event loop is busy. The same exception follows **today** from two queued presses of Generate (a double click) or Generate then Close. That probe raised on the second handler and would write two reports. So this is not a new class of defect. Inc 12 extends it to Reports, as the ten earlier dialog Escapes did elsewhere.
- **Fix (backlog, not owed by Inc 12):** one toolkit-wide guard. Each dismissing handler or action returns early when `not self.is_active`, with a test that queues two presses. Name it with D7-20's remaining dialogs or as a new BL row.
