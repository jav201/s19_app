## 3. Decisions taken at E1 (with reasons)

- **E1-D1 — D-4 by amending the definition, not by new rows.** Alternatives: (a) two new rows "when the CRC Designer is displayed after an in-place write …" and "when an in-place write ends while it is displayed …": their responses are exactly 002.5's and 002.1's, so they would be duplicates with a different trigger list (rule E3: alternatives sharing a response share a row); (b) **chosen:** widen *loaded image changes* — for every CRC Designer row an in-place write is an image change, and Inc 13 already marked the exclusion as the known gap routed here.
- **E1-D2 — the hook: one `app.py` helper called at the three write sites, calling a public CRC Designer method that reuses Inc 13's watcher logic.** Alternatives: (a) `self.mutate_reactive(S19TuiApp.current_file)` — Textual's idiom for an in-place mutation, but it also fires the app's `watch_current_file`, which re-plans the Split / Join window and calls `focus()` on its table (`segment_split_view.py:1744`) even while the window is hidden: a focus change on the Patch Editor, i.e. a UI change; rejected; (b) a new app reactive (an image-bytes counter) watched by the panel: decoupled, but a second "image changed" signal for one consumer today (speculative); (c) a listener inside `ChangeService`: a UI concern in the service layer; rejected; (d) **chosen:** `S19TuiApp._note_image_bytes_written()` → `CrcDesignerPanel.note_image_bytes_written()` → `_on_image_changed()` (Inc 13: schedule while displayed, mark stale while hidden). It sits next to each apply completion, as the plan row asked. A missing panel (headless trees) is tolerated as `watch_current_file` does. The apply site calls it after the `try`/`except`, so an apply that ends with `Patch Editor: <error>` after the journal restore also counts (R-CRC-PREVIEW-002.5/6).
- **E1-D3 — F-27 resolves names in the Check Editor from the ledger it already holds; Inc 4's resolver is reused through its output.** Inc 4's `_symbol_name_index` maps a name to a tag (name → address); F-27 needs address → name, so it does not fit. What does fit is its result: an entry the read resolved carries the tag's spelling (`entry.symbol`, R-CHG-SYM.9), and the named-parameter rule takes it first. The address rule reads the panel's normalized ledger rows (`{name: (address, size, fmt_unit)}`), the same list the operator sees; no second A2L index is built. Rejected: writing `symbol` into specs (the key exists in the v2 wire form, `io.py:1542`): every spec written that way would be refused on a read with no A2L (R-CHG-SYM.10, .12: a variant run in a project without an A2L file, a pick with no A2L loaded), a one-way change to the files operators keep. *(E3 A-6)* A symbol that names a listed parameter whose address or byte count differs from the entry's gives no named parameter; the address rule is not tried then, so an entry never names a different parameter than the one its spec named. Inc 4's reader already drops a symbol entry whose tag's address or integer length drifts from the wire (`io.py`, drift limb), so the case is reached only through the panel's spec load (R-CHKED-041.3/6, partial). *(E3 A-5)* The A2B diff report (R-DIFF-CHK.11, `diff_report_service.py:1591-1615`) names a spec entry by the first A2L/MAC symbol at its address and ignores size, ambiguity and `symbol`. The Check Editor's rule is stricter on purpose: including a parameter changes a field's identity (its expected bytes, its survival across an A2L change), while the report only labels a row. The two forms are deliberate; the batch-end canon fold aligns neither to the other.
- **E1-D4 — an ambiguous entry becomes a memory row.** When two or more parameters share the entry's address and byte count and no symbol names one, the system does not pick one (A2L order is an accident of the file). Case 08 has 0 such parameters (pilot: `params_sharing_address_and_size: 0` of 462); the planted twin A2L tests the rule. A duplicate entry (same named parameter twice) becomes a memory row, so the field count stays the entry count (R-CHKED-043's `(<n> fields)` stays true).
- **E1-D5 — "loaded from a spec" is tracked by identity, not by address.** Alternative: keep the spec's bytes for any field whose range equals a loaded entry's range — simpler, but then a field the operator excludes and includes again (or a memory row removed and added again) keeps the spec's bytes, which breaks R-CHKED-025 and removes the only way to re-baseline one field from the image. Chosen: memory rows carry their spec bytes in the row (a fourth tuple element, `None` for rows added in the session); parameters keep theirs in a dict pruned to the included names whenever the picks change. The prune reads the panel's current picks, so a stale queued `SelectionChanged` never removes a fresh entry; an exclude and include fast enough to be handled in one message batch keeps the spec's bytes. **Known limitation (E3 SEC5-4):** the operator meant to re-baseline that field from the image and Write keeps the spec's bytes; it happens only when both toggles are handled before the bubbled `SelectionChanged` reaches the panel (key repeat, a slow ledger repaint). R-CHKED-025/2's one pause pins the slow path. No wrong value reaches a saved file: the bytes kept are the spec's own declaration at its own address.
- **E1-D6 — a spec's bytes belong to their entry's range: they are keyed by (name, address, size)** *(amended at E3, SEC5-1 = A-1; was: "used only when their count equals the field's size")*. A parameter loaded from a spec keeps its spec bytes only while the ledger lists its name at its spec entry's address and byte count. When a repopulation lists it at another address, with another byte count, or not at all, the field becomes an unlabelled memory row at the spec entry's address with its byte count and bytes (R-CHKED-056), and the parameter is not re-included; included again by the operator, it is a field included in this session and reads the image at its new range (R-CHKED-025/3). Alternatives: (a) name-keyed bytes (E1): Write declares the spec's bytes at the new address and Validate judges an address the spec never covered — rejected (SEC5-1, HIGH); (b) drop the bytes and keep the pick reading the image (A-1's form): the operator's declaration is lost and the rewritten spec silently differs — rejected by the E3 ruling; (c) keep the pick by name and add the memory row beside it: Write gains an image-baselined entry the operator did not choose, and a resized parameter gives two overlapping entries at one address — rejected. The length check in `_check_items_to_document` stays as a backstop. R-CHKED-010 keeps its text; the definition *still lists* sets its scope.
- **E1-D7 — R-CHKED-054 is kept although F-26 does not reproduce.** F-26 is a plan finding; the row pins the behaviour so that the R-CHKED-010 fix (which touches the same repopulation path) cannot bring F-26 back.
- **E1-D8 — tests.** One new test file is proposed (`tests/test_b101_check_spec_and_designer_writes.py`; `EXPECTED_SCANNED_TEST_FILES` is re-measured at integration). Inc 13's `tests/test_b101_designer_recompute.py` is not edited: its D-2 AST guard compares named nodes with a base. One existing node body changes (`E1-slice.md` §3).
- **E1-D9 — a `string` entry of a picked spec** is loaded with its encoded bytes as expected bytes and is written back as a `bytes` entry with the same bytes (the Check Editor writes `bytes` entries only, `app.py` `_check_items_to_document`). The check result is the same; noted, no row.
