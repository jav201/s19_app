## Answers to the brief's questions

- **Is the hostile set complete?** No. See S-1 for the missing Windows and POSIX arms. Containment (S-2) is the backstop that makes a missed character harmless for *escape*. ADS, collisions and reserved names are still integrity and availability defects that containment does not catch.
- **Does "resolve then check containment" hold against symlinks and junctions?** Not as written. It must anchor to the work-area root and walk for reparse points, as `copy_into_workarea` and `_check_home_contained` already do (S-2). After that, the window between the check and the write needs a same-user attacker who can write inside the work area, which is out of this threat model. `os.replace` replaces a symlink at the final name rather than following it, so placing by replace is safer than today's `write_text`.
- **Is the staging design race-free on Windows, and does it never delete another writer's file?** Exclusive create plus a generated name removes the P-15 and P-5 races. Windows lock behaviour and the cleanup of the placeholder after a failure are not specified (S-6). The copy path must never move the source (S-5). D8 contradicts the never-delete invariant (S-4).
- **Does C8 cover markup injection?** In cells, yes. In reports and notifications, not explicitly (S-8). Addresses are integers and safe. Refusal codes are constants.
- **Is there a denial-of-service angle?** Yes, it can be contained (S-9). The S5 overflow is an availability false positive (S-10).
