# Investigation — read/write integrity of images, change docs and flow outputs (2026-10-22)

**Tree:** `main` @ `9793fcd` (probed in a detached worktree; no source or test was edited).
**Reviewer role:** security-reviewer (read-only). **Scope:** every path that reads an image / change doc / check doc / A2L / flow file, every path that writes bytes into an image, every writer of an image or report, and the status/report layers above them.
**Probes:** `.dev-flow/design/investigation-rw-2026-10-22/` (`p01`…`p14` + `common.py`). Run any probe with `S19_WT=<detached checkout>` and `PYTHONUTF8=1 PYTHONDONTWRITEBYTECODE=1`, interpreter `s19env`. Each probe works in its own temp dir and writes nothing inside the checkout. `common.py` includes an **independent minimal S19 and Intel HEX parser** (`mini_s19`, `mini_hex`) that shares no code with the repo, so a written file is checked by something other than the repo's own reader.

## 1. BLUF

**Verdict: BLOCK. The tool can write a file that differs from what it reports, and every layer above the writer reports `ok`.** The seed finding (a patch that applies nothing reports `ok`) is real. It is one case of a wider defect class, and it is **not a regression.** The PATCH arm has returned `ok` for every outcome since batch-44 (`1fcdca3`). Re-executed at `b8feb8a` (the tree P-31 was recorded on) and at `1fcdca3`, the same fixture gives `ok` / `applied 0 entries` on both. P-31's `error` cannot come from that code path. The premise was recorded wrong.

There are **ten HIGH findings**. Four of them change bytes in **every** flow or editor output, or turn a corrupt input into a clean `ok`:

1. **H-1: S0 header bytes are loaded as image data at address 0 and written back as a data record.** Every repo example with an S0 header (15 of the 16 `.s19` files under `examples/`) round-trips with 6–18 bytes at `0x0` that the source never declared as data. The repo's verify-on-save and diff reports cannot see this, because the reader and the writer share the same mistake (P03, P13, P14).
2. **H-2: the flow PATCH block is always `ok`.** This covers entries outside the image, straddling its end, inside a gap, a blocked document, a v1 document and **malformed JSON**. The WRITE-OUT block then writes the unpatched image, and the run, the chain-set report and the flow report all say `ok` / `CLEAN` (P01, P02c, P09).
3. **H-3: parallel chain-set lanes that share a WRITE-OUT name write each other's image.** In 5 trials of 8 lanes, 33 lanes reported `ok — wrote same.s19` while the file held **another lane's** bytes, and 2 lanes failed. The cause is the shared staging path `<workarea>/temp/<name>` plus a check-then-copy dedup (P02a).
4. **H-4: the Patch Editor's undo/remove does not revert the in-memory image.** After apply → undo → apply → save, the saved file holds the undone write. The summary lists only the last apply, and verify-on-save reports `verified` (P05).

The other HIGH findings are each narrower:

- **H-5:** the A2L physical→raw encoder writes multi-byte values little-endian under `MOD_COMMON BYTE_ORDER MSB_FIRST`. This is the write side of backlog H-7, which today is filed as a decode-only P3.
- **H-6:** the COMPU_TAB inversion writes the nearest or clamped table value with no flag (request 500, written raw = 20.0).
- **H-7:** a CRC block whose region covers no image bytes injects the CRC of an empty stream, `00000000`, over live image bytes, and reports `ok`.
- **H-8:** truncated S19 and HEX files (no terminator / no EOF record) load as `ok` with the missing bytes simply absent.
- **H-9:** an A2L `MEMORY_SEGMENT` name containing `../` makes Split/Join/Export write **outside the work area**.
- **H-10:** `ChainRunOutcome` and both report writers drop the per-entry dispositions and refusals, so no record of a run shows what was not applied.

**What was verified clean:** the S19 and HEX emitters are byte-exact for every address map they are given. 200 random sparse maps (S19 + HEX) were checked with the repo loader and the independent parser: 0 mismatches. Checksums, byte counts and S1/S2/S3 width selection are correct. The core apply engine (`apply_change_document`) classifies `applied` / `skipped-*` / `blocked` correctly. The defects are in what the layers do with those dispositions, and in what the loaders feed the emitters.

## 3. Truthfulness chain — where each layer drops the signal

```
apply_change_document → ChangeSummary.counts / entries[*].disposition     ✔ correct
        │
run_flow PATCH arm    → BlockResult.status = "ok" always                  ✖ H-2 (drops dispositions + refusals from status)
                       → FlowRunResult.change_records / refusals           ✔ retained
        │
run_chain_set         → ChainRunOutcome (status, block_results, paths)    ✖ H-10a (change_records, refusals, image_ranges dropped)
        │
Flow Execution lanes  → painted from outcome.status / block_results       ✖ shows ✓ ok (flow_screens.py:3305-3380)
chain-set report      → status + inputs only                              ✖ H-10b (no dispositions, no refusals, no written paths)
flow REPORT           → applied records only; Status CLEAN                ✖ H-10c
Patch Editor status   → "Apply: N applied, M skipped, K blocked"          ✔ truthful (but H-4 on the image)
```
