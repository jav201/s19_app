El riesgo central: tests acoplados al módulo

  • 168 imports de S19TuiApp desde s19_app.tui.app: se conservan con re-exports; cero cambios.
  • 39 nombres parcheados vía app_module.X (SaveProjectPayload, parse_a2l_cached, write_project_manifest, os…). Si el método que usa X se muda de módulo, parchear app_module.X deja de afectarlo: el test falla o, peor, pasa sin probar nada. D1
  • ~30 tests leen el texto fuente de app.py (leyes estructurales, censos AST) y 11 el de screens_directionb.py. Hay que apuntarlos al paquete y probar que siguen pudiendo fallar.
  • Constantes de screens_directionb parcheadas por alias (CHECK_GLYPHS 24 usos, A2LParameterPicker 10): mismo problema que D1.

Prueba de equivalencia (sin modelo)

  • Identidad de cuerpos: cada método y función del archivo viejo existe exactamente una vez en el paquete nuevo, con AST idéntico salvo las referencias reescritas por D1. El MRO de S19TuiApp resuelve cada nombre al mismo cuerpo.
  • Suite completa antes/después en el mismo runner: el conjunto de nodeids passed/failed/skipped es idéntico (los 5 fallos heredados incluidos).
  • Controles negativos: el verificador rechaza un método perdido, uno duplicado y un cuerpo alterado.
  • El script es re-ejecutable: si Inc 1b cambia algo después, se vuelve a correr sobre la base nueva en lugar de resolver conflictos a mano.
