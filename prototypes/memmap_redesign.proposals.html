Memory Map screen — three redesign directions

Design proposal only — no repo change. Grounded in s19_app/tui/screens_directionb.py (MemoryMapPanel, batch-45/47/67 lineage), styles.tcss, entropy_style.py and the shipped docs/images/memory-map.png capture. Method: /tui-design (brief → hierarchy → budget → variants → critique). 2026-08-01.

BLUF. The screen's hero element — the entropy band bar — is honest but useless on the images this tool exists for: it scales linearly over the full address span (~128 MiB in the shipped example) while the mapped payload is 1,030 B, so ≈98% of the bar is gap hatch and all five regions collapse into a one-column sliver. Everything else (a "Coverage: 0.00%" readout, an empty inspector, a permanent 4-row legend, no keyboard path) follows from the same flat hierarchy. Recommendation: Variant A (gap-fold bar) + the five cross-cutting fixes as one fast-dev-flow batch; Variant B (two-lane map) parked as an optional follow-up; Variant C adopted only for its two portable ideas.

2 · Findings

Each finding cites its code anchor. Severity is about operator cost, not code quality — the implementation is disciplined (B3 markup safety, class-based remounts, no re-derivation per LLR-041.7); the defects are design-level.

#FindingEvidenceSeverity
F-1 The hero collapses on sparse images. Segment width is round(60 · run_bytes / total_span) — proportional to the address span. S-record firmware is sparse by nature, so the normal case renders as ~59 cols of ╱ hatch + a 1-col sliver holding every region. The bar answers neither "what's in the image" nor "where". screens_directionb.py:2066 (seg_width), :2057 (gap hatch), :230 (_BAND_BAR_WIDTH=60) HIGH

3 · Design brief

  • Posture: glanced at, then operated. Job: "what kinds of bytes does this image hold, where, and take me there." Task flow: load → glance bands → select region → inspect → open in hex.
  • Hierarchy target: one hero (the payload picture), one secondary (region list/selection), everything else demoted. Rank by area/brightness/space — the terminal has no type scale.
  • Invariants kept (all variants): B3 — no file-derived text in rows/bar; color only via band-* classes + texture glyphs (C-10 color-blind cue); presentational panel — no new analysis (LLR-041.7); class-based remounts (DuplicateIds); 80×24 floor and the width-narrow reflow regimes; the N4a single=inspect / double=hex split.
  • Budget: every variant stays in the cheap cost class — widgets are rebuilt only on file load / unload (no per-tick derivation); the fold computation is O(regions). No headroom risk.

4 · Variant A — Gap-fold band bar RECOMMENDED

Thesis: keep the linear bar's honesty, but spend the 60 columns on mapped bytes. Any gap wider than its fair share of columns folds into a fixed 2-col ╱╱ axis-break marker labeled with its humanized size. Region widths become proportional to mapped bytes. The ruler stops being 5 linear ticks and becomes edge labels under region starts — every label now names a real address.

What changes

  • _build_band_widgets: allocate bar columns over total_mapped_bytes; emit a fixed-width .map-band-gap fold marker per gap (1 col if the gap is < the fold threshold, 2 cols + label otherwise). A dense image with no dominant gaps renders exactly as today — the fold is a no-op when every gap fits its proportional width.
  • MapRuler → edge-labeled ruler: one label per region start (collapsing labels that would overlap), fold labels carry the humanized gap size. LLR-072.3's "5 linear ticks" is amended — a requirement amendment (Before/After) goes in the batch spec.
  • Stats strip → one line, dual readout (mapped vs span), humanized gap (F-2).
  • Legend row → demoted to the footer hint (k already opens LegendScreen app-wide); frees 4 rows (F-4).
  • Inspector auto-selects region 1 on render (F-3) — never empty with a file loaded.

5 · Variant B — Two-lane map FOLLOW-UP CANDIDATE

Thesis: sparse truth and payload detail are two different questions — give each its own lane and link them with a selection cursor. Lane 1 keeps today's span-linear strip (the honest "where in the address space"). Lane 2 renders mapped bytes only, thick (2 rows), with the region's own entropy profile drawn inside using half-block texture. The selection cursor renders on both lanes — the signature element renders the relationship between address truth and payload.

Assessment

AxisAssessment
FixesF-1 (payload lane), F-3/F-5 (cursor + keys are the model), F-6 (span lane keeps only endpoint labels)
Strength✅ Best posture fit: the linked cursor makes "where am I in address space vs in the payload" a rendered fact, and it renders — the strongest signature of the three.
Cost⚠ 2 lanes + profile row + inspector strip consume ~8 rows before the region list — tight but workable at the 80×24 floor (list scrolls). New per-region sparkline sampling (still load-time only). Roughly 2× Variant A's diff.
Risk⚠ New selection state + two synchronized lanes = more surface for the vacuous-acceptance failure mode this project keeps catching. Needs a real counterfactual per lane (cursor moves on both, not just one).

6 · Variant C — Inspector-led region table ADOPT IDEAS ONLY

Thesis: the region list already answers the operator's questions — make it the hero (aligned columns, log-scale size bars, per-region entropy profile column), demote the bar to a 1-row folded address strip, keep the inspector always populated.

Strength✅ Log-scale size bar fixes today's lie-by-omission (a 6 B and a 256 B region both render 4-cell bars ≈ equal); aligned columns read faster.
Weakness❌ Demoting the bar makes the hero a table — it labels rather than renders (the tui-design signature test fails). Largest information-architecture change for the least distinctive result.
Verdict⚠ Don't build as a variant. Port two ideas into A: log-scale microbar denominators, and column-aligned region rows.
